Build graph content with `edit_graph_draft`, in small edits answered by a compile report. The persisted draft is not accepted Notebook content; only a learner-approved Confirmation applies it. A Personal scope is already a Patch; publication is not part of this procedure.

1. Write the designed Nodes. Each Node asserts one capability, with `display:label` and `pedagogy:criterion` in a Metadata set attached to its UUID. The criterion is the demonstration from the design, with its conditions when the Node is a simpler-conditions step of a larger task. pedagogy:knowledge-type and pedagogy:threshold are optional authoring notes. When the learner chooses a method, attach one `pedagogy:guidance` list of `{ text, mode: "append" }` entries to its strand tag, with their choice verbatim and its instructional order. Define that tag's complete current Node membership, including newly elaborated Nodes; the method must survive Mission approval and a fresh Lesson without this conversation. For a learner override, author a distinct Metadata-set id with append or explicit `{ replace: [{ name: "strand-tag" }] }` / `{ keep: [{ name: "strand-tag" }] }` target refs; reusing an inherited set id/property replaces its whole list. A recommendation or unchosen alternative is not their choice. A strand the learner wants to be able to do is a capability with its own criterion and Mission target, even when it is not necessary for another target. A way of learning used only to serve another capability is guidance on its strand tag, not a Node. `pedagogy:elaborate: true` marks a Node whose prerequisites are not charted yet, and `warnings` reports it as `coarse`; when you chart them, set it to `false` in the same diff. Materials (Problems, cards, Documents) are lazy, not prerequisites for charting. Use `pedagogy:milestone: true` for section ends; sections follow the order of `targets`. Edges express only real prerequisites; express “teach this earlier” with `pedagogy:priority`, usually on a tag: a small integer, higher first, absolute across the map, inherited by members unless a Node overrides it. A `define-tag` named `lesson:<name>` groups Nodes taught well together (siblings to tell apart, or a step and its immediate use); milestones remain alone. Each milestone's criterion or guidance names a simpler-conditions ladder for integration correctives, from the lowest viable whole task back up to its full capstone conditions. Groups cannot cross sections or straddle an outside prerequisite; read `lesson-split` warnings and revise them. The numbered path is derived, not separately authored.
2. Each Edge's `from` is the prerequisite and `to` is the dependent: basic clauses → integrated reading, not the reverse. The host's path follows incoming Edges from a target to its prerequisites. Test each Edge: can the dependent be demonstrated without the prerequisite? Only "no" warrants necessity; write the reason in the Edge's pedagogy:because. A harder-conditions task depends on its simpler step only when that step is needed, not merely taught first. Teaching order, presentation and methods are not Edges. Keep an independently wanted practice capability reachable by targeting it, not by asserting a false necessity. A dependent with more than a few prerequisites is a grain defect or a list of helpful context: split the capability or drop the Edges, never keep them as emphasis. The host reports cycles and dangling endpoints after each draft edit; an invalid intermediate draft is kept. Read that report and fix it before proposing, rather than computing reachability yourself.
3. Ground the content in the learner's actual target and available trusted sources. Explain uncertainty, rather than fabricate corroboration or a Hub result.
4. Use `edit_graph_draft({operations:[...]})`: `put` carries one SemanticOperation and replaces the entry with its entity key; `delete` removes a returned key. Relabel by putting the same metadata-set id again, including every property it should retain. Set `targets` with `nodes` to include every wanted performance strand's final milestone, in the order the learner wants them reached, including independent practice capabilities, and `summary` with `summary`, `sources` and any observation `cites`. Keep a learner's verbatim already-known report on the draft Node whose whole criterion it covers with `claim` (`node`, `statement`, optional `prompt`); approval records and attaches it through `record_claim` and `attach_claim`. `delete` with `claim:node-id` removes it; the tool description covers placement. Resume an open draft listed in context with `draftId` on the same Session scope; it survives Session expiry. A lone `discard` throws it away.
5. Submit the Session's draft with `propose_graph_diff({})`, or include it automatically with `propose_mission` using matching targetNodes. Neither proposal accepts inline graph operations. Declining leaves the draft open for more edits. Wait for acceptance and successful application before referring to the Nodes as existing. A failed Confirmation is not a saved edit.

## Structure guidelines

- Different task presentations → one capability Node, not separate identities.
- Unclear grain → ask whether the parts have different necessary Edges.
- Same capability in a revision → retain UUID; a new UUID is a new identity.
- Removed identities → successors are provisional hints, not evidence. The theory's update and background content pass own record homes, not graph Edges.
- Unavailable edit affordance → discuss the proposed content without claiming that a Node, View, item or material has been saved.
