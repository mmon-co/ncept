Build graph content with `edit_graph_draft`, in small edits answered by a compile report. The persisted draft is not accepted Notebook content; only a learner-approved Confirmation applies it. A Personal scope is already a Patch; publication is not part of this procedure.

1. Write the designed Nodes. Each Node asserts one capability, with `display:label` and `pedagogy:criterion` in a Metadata set attached to its UUID. The criterion is the demonstration from the design, with its conditions when the Node is a simpler-conditions step of a larger task. pedagogy:knowledge-type, pedagogy:threshold and pedagogy:guidance are optional authoring notes; guidance is where the chosen method goes. `pedagogy:elaborate: true` marks a Node whose prerequisites are not charted yet, and `warnings` reports it as `coarse`; when you chart them, set it to `false` in the same diff. Materials (Problems, cards, Documents) are lazy, not prerequisites for charting. Use `pedagogy:milestone: true` for section ends and numeric `pedagogy:sequence` for tie-breaking teaching order. A `define-tag` named `lesson:<name>` groups Nodes taught well together (siblings to tell apart, or a step and its immediate use); milestones remain alone. Groups cannot cross sections or straddle an outside prerequisite; read `lesson-split` warnings and revise them. The numbered path is derived, not separately authored.
2. Test each Edge: can the dependent be demonstrated without the prerequisite? Only "no" warrants necessity; write the reason in the Edge's pedagogy:because. A harder-conditions task depends on its simpler step only when that step is needed, not merely taught first. Teaching order and presentation are not Edges. A dependent with more than a few prerequisites is a grain defect or a list of helpful context: split the capability or drop the Edges, never keep them as emphasis. The host reports cycles and dangling endpoints after each draft edit; an invalid intermediate draft is kept. Read that report and fix it before proposing, rather than computing reachability yourself.
3. Ground the content in the learner's actual target and available trusted sources. Explain uncertainty, rather than fabricate corroboration or a Hub result.
4. Use `edit_graph_draft({operations:[...]})`: `put` carries one SemanticOperation and replaces the entry with its entity key; `delete` removes a returned key. Relabel by putting the same metadata-set id again, including every property it should retain. Set `targets` with `nodes`, and `summary` with `summary`, `sources` and any observation `cites`. Keep a learner's verbatim already-known report on a draft Node with `claim` (`node`, `statement`, optional `prompt`); approval records and attaches it through `record_claim` and `attach_claim`. `delete` with `claim:node-id` removes it. Resume an open draft listed in context with `draftId` on the same Session scope; it survives Session expiry. A lone `discard` throws it away.
5. Submit the Session's draft with `propose_graph_diff({})`, or include it automatically with `propose_mission` using matching targetNodes. Neither proposal accepts inline graph operations. Declining leaves the draft open for more edits. Wait for acceptance and successful application before referring to the Nodes as existing. A failed Confirmation is not a saved edit.

## Structure guidelines

- Different task presentations → one capability Node, not separate identities.
- Unclear grain → ask whether the parts have different necessary Edges.
- Same capability in a revision → retain UUID; a new UUID is a new identity.
- Removed identities → successors are provisional hints, not evidence. The theory's update and background content pass own record homes, not graph Edges.
- Unavailable edit affordance → discuss the proposed content without claiming that a Node, View, item or material has been saved.
