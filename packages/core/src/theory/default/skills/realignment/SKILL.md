# Realignment

1. Read `theory {name:'warnings',input:{scope}}`, `theory {name:'mission',input:{scope}}`, `theory {name:'trail',input:{node}}`, and `theory {name:'items',input:{node}}`. Warnings report item outcomes, edge contradictions, instability, unused content, homeless Records and self-report contradictions. None is proof of a content defect; inspect the cited task/response first.
2. Wrong task/outcome recording → explain the local correction rather than changing content. Defective edge or capability grain → graph authoring. Defective task or exposition → quiz authoring or material work. Goal/View drift → revise the existing Mission through its Confirmation, keeping its View identity and citing the current Record; use new targets when the goal moved, a new Mission for a second goal, or retirement when the learner no longer wants it. All require learner approval.
3. Use Material changes only where `material` is mounted; graph draft changes require an allowed Chart transition. With the learner's edit-session authority, propose only the supported host graph change and wait for Confirmation before applying it. Explain which retained UUIDs still assert the same capability and which are removed.
4. The host supplies effective observations and the graph-change input to the theory's event Program; declared successors give provisional homes only. The host-owned background sweep refines pending task homes by content; it is not an interactive tool. Read `theory {name:'trail',input}` and `theory {name:'warnings',input}` under the new revision, preserving effective homing observations on every read. Homeless Records remain visible, not discarded or silently declared learned.
5. Recount the change and its effect on cited Records. Do not promise changes to other Profiles or publication workflows.
